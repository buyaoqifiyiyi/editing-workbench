# 剪辑工作台维护层

维护目标是让`editing-workbench`统一入口及本机引擎更容易作出正确的创作判断和软件执行选择。剪映与达芬奇是工作台内部持续适配的后端；剪映尚未完成的能力继续沿用主表、任务清单和固定缺口台账推进，不因数据不互通或默认后端变化而降为历史备份。原始数据、实现、配置和执行路径保持可用，各后端分别验证。先读当前Skill、工作区约束和相关调用方；只改有具体依据的部分，不把文档、教程、规则或效果数量当作能力提升。

## 内容边界

| 位置 | 保留内容 |
|---|---|
| 创作决策指南 | 方向分流，以及贯穿选段、声画、镜头连接、技法取舍与修订的判断流程；不复制执行能力表 |
| 剪辑指南与参考 | 执行规则、按问题检索的镜头方法、能力契约、格式、工具代码与必要的原生资源描述；剪映能力以`references/capabilities.md`为主表，其他宿主按对应后端指南，不互相继承准入 |
| 工作区 `Skill维护层/来源` | 教程观片原文、旧版能力文档等历史来源；Skill 内只保留提炼后的方法与出处文件名 |
| 本维护指南 | 优化原则、经验准入标准、维护流程和核验边界 |
| 剪辑工作区的各项目目录 | 素材、计划、草稿、字幕、抽帧、截图、完整案例和项目反馈 |
| 工作区的 `Skill维护层` | 本次变更说明、最小来源索引、修改前备份、必要验证结果 |
| 外部运行数据目录 | 模板索引、逐项目准入记录、本机路径与检验报告 |

素材、草稿、完整计划、项目生成器、测试媒体、截图、逐项目统计、验证日志和本机模板清单均不得写入引擎包及兼容 Skill。本维护层也不复制剪辑项目；证据索引指向原位置。必要依赖、执行脚本及不含项目素材的原生契约描述可以保留，不能为了减少体积删除执行所需内容。教程/作品的出处链接与真正影响判断的方法可留；逐条观片日志、封面汇总与完整结构另存工作区。

## 优化原则

1. **经验先于资料。** 把“项目发生了什么”改写为“遇到什么条件，应如何行动，怎样判断有效”。删除人物名、作品名、盘符、项目秒数和轨数后仍能指导新任务，才适合进入剪辑 Skill。
2. **收敛到已有规则。** 先查重复、冲突和调用者；优先修订现有段落，再考虑新增引用。一个原则保留一个主要位置，其余按需链接，不按每个项目新建一份经验文档。
3. **保留适用条件。** 单次成功先按该条件保存，不写成所有素材都适用的配方。文案、构图、节奏、声音和兼容性分别判断；整体认可不抹掉局部问题。
4. **事实、推断和偏好分开。** 用户反馈准确记录在项目；根因未查明时不编成事实。把可核实的方法和授权边界写成规则，作者身份、台词、数据及来源不足时保留不确定性。
5. **不提升证据等级。** 区分计划/结构、参数回读、原生静帧、编辑保存重开、完整视听与导出；通过哪一层只声明哪一层。待办、资源存在、协议 accepted、队列 succeeded 都不等于计算完成。用户最终检查/导出的分工保持有效。
6. **能力按子集准入。** 新能力必须有真实输入、契约与可复核结果，覆盖实际 validate/build/verify/publish/交付路径及必要拒绝边界。环境或实现指纹变化时重新验证，不手工改 passed，不复制旧工程冒充后台重建。
7. **让内容决定表现。** 文案有镜头依据和前后呼应；运动有可辨认的起止状态；复杂变化后恢复清楚主体。数量和复杂度不能替代表达；不设最低效果数、固定时长或统一创作公式。
8. **维护范围可控。** 普通剪辑不自动改 Skill。用户要求维护才落盘；本次授权只覆盖当前维护任务，不创建周期任务，也不自动恢复暂存效果、研究画质增强或增加前台操作。
9. **新增规则须抵偿成本。** 写明它修正的真实错误或影响的决策；仅换措辞、重复提醒、堆统计和没有现实需求的抽象不入库。审查上下文负担与工具兼容成本，优先删重复。
10. **证据外置且可追溯。** 项目原位保留；维护记录保存来源定位、提炼理由、变更文件及验证范围。测试用隔离目录，结束清理临时媒体/草稿，留最小回执；不清理仍被正式工程引用的素材。

## 经验准入

逐条判断候选经验：它解决什么实际问题？支持证据是什么？是否区别于已有规则？适用条件是什么？后续 Agent 能采取什么行动？怎样发现失效？

- 有证据、可迁移、可执行且无重复：合并到最接近的现有规则。
- 只有项目数值、完整做法、用户原话或一次结果：保留在项目/维护记录，不进入本体。
- 原因或输出尚未验证：保留研究假设及下一步验证方法，不登记为正式能力。
- 已过期、重复或与现行边界冲突：替换/合并并更新调用者，历史证据保存在 Skill 外。

文档维护不等于模型训练。是否变好要看下一次真实剪辑能否正确应用经验，不能用 frontmatter 校验通过证明审美或剪辑质量提升。

## 执行与核验

在用户当前工作区建立 `Skill维护层/变更/<日期-事项-版本>`，备份将修改/移出的文件；记录实际位置，不把本机绝对路径写入本维护指南。追踪脚本、文档和配置调用，外置数据前核实读写入口与原有准入机制。

先完成最小修改，再检查受影响 Skill 的 frontmatter、本地引用与标题锚点、重复和残留项目内容。能跑的就别靠眼睛：工作区 `Skill维护层/工具/entry_point_check.py`（离线入口的旧措辞，`--root` 默认仓库根，默认只读）与 `Skill维护层/变更/2026-10-16-回归证据路径约束-v1/doc_check.py`（frontmatter、本地链接与锚点；实际活动Skill目录与runtime作参数传入，历史记录目录不搬动）、`Skill维护层/工具/ledger_check.py`（复算 `Skill维护层/{变更,来源}/*/hashes.txt` 历史台账，`--root` 默认工作区根、只读：受保护区（`engine/`、`skills/`、`Skill维护层/`，以及三点同步的两个安装点 `.codex/skills`、`.dsh/skills`）里某个路径**没有任何一条**记录与现文件相符、或记录过的文件没了，才 rc=1；区外漂移、「位置没定论」与机器产物只报告；`Skill维护层/{变更,来源}` 的一级子目录缺 `hashes.txt` 同样 rc=1——目录在、台账不在，那一轮改动就无法复算；`--self-test` 用一次性夹具证明各档真的分得开）。分流规则只在决策层维护；改动后检查剪辑层的交接句、两个 description 与 openai.yaml 没有重复分流细节。调整数据读取或执行逻辑时，用 `paths`定位的`runtime/scripts/run_checks.py`（可加 `--only`）运行覆盖该真实路径的现有回归；它会自动生成合成素材，并对缺剪映用户数据、非 Windows 或缺外部计划的检查标明跳过原因，跳过不等于通过。新增执行逻辑时在其中登记对应检查，登记由 `paths`定位的`runtime/scripts/coverage_self_check.py` 兜底：它从注册表出发沿 import 关系遍历 `scripts/`，未登记的检查脚本、没有检查用到的脚本、注册表指向的缺失文件都会让它失败（`--self-test` 用一次性夹具证明这三条规则真的会报）。同时证明原数据哈希未变、迁移后可读、缺失配置有明确错误、准入仍会拒绝过期记录；不要为文档改字重跑全部媒体测试。

将验证结果与受保护文件哈希写到外部维护目录；备份中保留历史路径是正常的，运行中的 Skill 不应依赖项目档案。记录里的复验期望值写成与整树规模无关的断言（rc/状态、各桶为空或非空）；**会被后续轮次改的文件**（本 SKILL.md、README、工具脚本）只写关系断言（「三处同哈希 / distinct = 1」「落 verified」），别写死值——写死的值下一轮就成了假话；一次性冻结的证据（备份、证据 json）才可以写具体哈希；整树计数和行数会随轮次增长，只能标注时点当历史参照。发现新问题时收窄修改或补齐必要验证。交付实际变化、可打开的原则与记录、已验证范围和剩余限制，不把未运行的前台/播放/导出写成通过。


## 独立引擎维护入口

执行代码、必要资源和本指南只维护 engine/src/jianying_engine/runtime。旧 Skill 的 scripts/assets/references/guides 是兼容连接，不分别复制修改。新增 CLI 操作在 api 白名单登记；MCP 共用该白名单。先跑受影响的运行时检查与包接口测试，再从 wheel 的隔离安装核验资源完整性；凭据、模型与项目数据不得打入 wheel。历史记录中的三处同步表示兼容入口指向同一源码及指南内容一致，不要求再维护三份实现。
